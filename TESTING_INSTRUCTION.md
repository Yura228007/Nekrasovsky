# Инструкция по тестированию Nekrasovsky (от А до Я)

## Часть 1. Сброс БД и первый запуск

### 1.1. Сброс базы данных (PostgreSQL)

**Вариант A — полное удаление базы (рекомендуется):**

1. Откройте **pgAdmin** или **psql**.
2. Подключитесь к серверу PostgreSQL (обычно `localhost:5432`, пользователь `postgres`).
3. Выполните:
   ```sql
   DROP DATABASE IF EXISTS "Nekrasovsky";
   CREATE DATABASE "Nekrasovsky" OWNER postgres ENCODING 'UTF8';
   ```
4. Либо через psql в консоли:
   ```bash
   psql -U postgres -c "DROP DATABASE IF EXISTS \"Nekrasovsky\";"
   psql -U postgres -c "CREATE DATABASE \"Nekrasovsky\" OWNER postgres ENCODING 'UTF8';"
   ```

**Вариант B — только откат миграций (если не хотите удалять БД):**

В папке `server` выполните:
```bash
dotnet ef database update 0 --project server
dotnet ef database update --project server
```
Это удалит все таблицы и применит миграции заново. Роли и права будут созданы сидером при старте сервера.

### 1.2. Строка подключения

Проверьте `server/server/appsettings.json`:
```json
"ConnectionStrings": {
  "DefaultConnection": "Host=localhost;Port=5432;Database=Nekrasovsky;Username=postgres;Password=admin"
}
```
Измените `Password` на ваш пароль PostgreSQL, если он другой.

### 1.3. Запуск сервера

1. Откройте папку `server` в терминале.
2. Выполните:
   ```bash
   dotnet run --project server
   ```
3. Дождитесь сообщений:
   - `Applying ... pending migration(s)...` или `Database is up to date`
   - `First user created: login=admin, password=admin` (если БД была пустая)
4. Сервер слушает: **HTTP http://localhost:9000** (и при необходимости HTTPS 5001).

### 1.4. Первый вход в приложение

- **Логин:** `admin`  
- **Пароль:** `admin`  

После входа откроется **Админ-панель** (роль Администратор/Владелец).

### 2.4. Материалы (сразу с приёмкой и ответственным)

В системе **материал добавляется вместе с приёмкой**: при создании материала вы указываете **склад** (куда принимаете), **количество** — и **ответственным за это количество назначается тот пользователь, под которым вы сейчас залогинены**. Отдельного шага «только приёмка без материала» нет: материал + склад + количество = приёмка и назначение ответственности на текущего пользователя.

**Порядок действий:**

1. Сначала создайте **склады** (п. 2.3) и **пользователей** (п. 2.2).
2. Раздел **«Материалы»** → кнопка **«Добавить»** (или аналог).
3. Вводите: **название**, **код (артикул)**, при необходимости описание, **ед. изм.** (шт, кг, л и т.д.).
4. Далее система запросит **выбор склада** и **количество**. Если укажете количество > 0 и склад — будет создан остаток на этом складе и **ответственным назначитесь вы** (текущий пользователь).
5. Чтобы ответственным был другой человек (например, старший кладовщик или утильщик), нужно **выйти и зайти под этим пользователем** и уже под ним добавлять материалы с приёмкой на нужный склад. Либо добавить материал под admin, затем в карточке материала выбрать **«Изменить ответственное лицо»** и назначить другого пользователя.

**Кого использовать для приёмки (под кем логиниться):**

- **admin** — можно всё добавлять под ним; потом через «Изменить ответственное лицо» раздать ответственность Новикову, Козловой, Утильщику и т.д.
- **Новиков** (старший кладовщик) — зайти под ним и принять материалы на **Основной склад** (так он будет ответственным за основной склад).
- **Козлова** (кладовщик) — принять часть на **Склад готовой продукции** или другой склад, если нужно.
- **Утильщик** (util) — зайти под ним и принять те же материалы (гранулы, красители) на склад **Утиль** в малых количествах как брак/отходы, чтобы тестировать сценарий «отправка на ЭКО» и списание.

**Таблица материалов для ввода** (название, код, ед.изм.; склад и количество выбираете при добавлении, ответственный = текущий пользователь):

| MAT-02 | Полиэтилен гранула   | кг     | Основной склад, 300 кг    |

### 2.7. Рецептуры (связь продукт — материал)

**В приложении нет раздела для настройки рецептур.** Связь «продукт — материал» (рецептура) есть только на сервере (API), в UI её не настраивают.

Для теста **переработки** и **выпуска** достаточно создать **продукты** (п. 2.5) и **материалы** (п. 2.4). Рецептуры можно не трогать. Если в будущем понадобится настраивать состав продукта — это делается через API (например, POST/GET api/Recipes).

---

### 2.8. Доступные перемещения (откуда → куда можно переносить)

**В приложении нет раздела «Доступные перемещения».** Правила «с какого склада куда можно переносить какой материал» настраиваются только на сервере (API или БД).

Для теста **заявок на перемещение** сначала создайте склады, материалы и пользователей (п. 2.2–2.5). Если при создании или одобрении заявки появится ошибка вроде «перемещение запрещено» или «такое перемещение не разрешено» — значит, для пары «склад-источник → склад-назначение» и материала нужно добавить запись в таблицу доступных перемещений (через API или напрямую в БД). Конкретные пары зависят от вашей логики (например: Основной склад → Цех экструзии, Цех → Утиль, Утиль → ЭКО). Этот шаг можно пропустить и вернуться к нему при появлении ошибки заявки.

---

### 2.9. Остатки и ответственность (уже созданы в п. 2.4)

Остатки на складах и ответственные лица создаются **при добавлении материалов** (п. 2.4): вы указываете склад и количество — система создаёт остаток (FillingWarehouse) и назначает **текущего пользователя** ответственным (ResponsibilityFilling). Отдельного шага «только приёмка» нет.

Что уже должно быть после п. 2.4:

- **Основной склад** — остатки MAT-01 … MAT-10; ответственный — тот, под кем вы их принимали (например Новиков или admin).
- **Утиль** — те же материалы (MAT-01, MAT-02 и т.д.) в малых количествах как брак/отходы; ответственный — Утильщик, если вы принимали под ним (см. конец п. 2.4).

Дополнительно при необходимости:

- **Цех экструзии / Цех покраски** — остатки появятся после **заявок на перемещение** с основного склада: создать заявку, одобрить её — материалы переедут в цех, ответственность перейдёт получателю (или останется у отправителя в зависимости от логики).
- **Склад готовой продукции** — продукты (PRD-001 и т.д.) принимаются через раздел продуктов/партий (если там есть приёмка на склад и назначение ответственного); либо через выпуск продукции (раздел «Выпуск»), после чего остаток и ответственность появятся на складе.
- Если нужно **переназначить ответственного** (например, часть с admin на Новикова) — откройте карточку материала в разделе «Материалы» и выберите **«Изменить ответственное лицо»**.

После этого можно тестировать заявки, передачу смены, переработку, утиль, выпуск. Если чего-то не хватает — доложить приёмку (добавить материал с приёмкой на нужный склад под нужным пользователем) или провести заявку.

## Часть 5. Типичные проблемы

1. **Не подключается к БД**  
   Проверить: PostgreSQL запущен, строка подключения в `appsettings.json`, пароль и имя БД.

2. **После сброса БД нет пользователей**  
   Убедиться, что при старте сервера выполнился сидер первого пользователя (логин `admin`, пароль `admin`). В логах должно быть: `First user created: login=admin, password=admin`.

3. **Приложение не видит сервер**  
   В коде клиента проверьте базовый URL (например `http://localhost:9000` для Windows, для Android — IP ПК в сети). См. `ApiService.GetBaseUrl()`.

4. **Нет прав на действие**  
   Проверить роль пользователя и привязку прав в **Права ролей** (RolePermissionsPage). Для admin логина часто действует полный доступ по коду.

5. **Ошибки при перемещении/переработке/утиле**  
   Проверить: остатки на складе (FillingWarehouse), назначенную ответственность (ResponsibilityFilling). При ошибке заявки «перемещение запрещено» — добавить доступное перемещение через API; рецептуры в UI не настраиваются.

6. **Проверка смены ответственного через Swagger**  
   - Запустите сервер (порт 9000 по HTTP или 5001 по HTTPS).  
   - Откройте в браузере: `http://localhost:9000/swagger` (или `https://localhost:5001/swagger`).  
   - Найдите **POST** `/api/responsibilities/material/{materialId}/assign` (или `.../product/{productId}/assign`).  
   - Нажмите **Try it out**.  
   - **Обязательно** заполните заголовок **X-User-Id** — ID пользователя, от имени которого выполняется запрос (владелец/админ или пользователь с правом ManageResponsibility). Например: `1` для admin.  
   - В **materialId** (или **productId**) укажите существующий ID материала/продукта.  
   - В **Request body** укажите JSON, например: `{"userId": 2, "quantity": 100, "measuringUnit": "кг"}` (userId — кому назначаем ответственность).  
   - Нажмите **Execute**.  
   - Если ответ **403** — заголовок X-User-Id не передан или пользователь не имеет прав.  
   - Если ответ **500** — в теле ответа смотрите поле **detail**: там текст исключения с сервера (например, не найден пользователь или материал).  
   - Успех: **200** и в теле `message: "Responsibility assigned"` и объект `responsibility`.

Если после прохождения всех пунктов что-то падает или не совпадает с ожиданием — опишите экран, действие и текст ошибки (из UI или логов сервера) для точечного исправления.
